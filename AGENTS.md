# Repository Guidelines

## Project Structure & Module Organization

- `src/cli.ts` is the executable entry point; `src/cli/` contains command wiring, argument handling, and presentation.
- `src/core/` contains the manifest, coordinate, discovery, source, resolution, installation, and Git-domain logic. Keep filesystem/domain behavior here rather than in command handlers.
- `test/` contains Vitest suites named `*.test.ts`; `test/helpers.ts` provides isolated temporary homes and skill fixtures.
- `docs/` holds the project brief and supporting documentation. `dist/` is generated by the build and should not be edited or committed.

The tool is manifest- and symlink-based: avoid introducing a database or hidden state. Changes that alter manifest output or discovery rules should update `README.md` and relevant tests.

## Build, Test, and Development Commands

Run `npm install` after cloning. Useful commands are:

```bash
npm run dev -- list       # run the CLI directly from TypeScript
npm test                  # run the Vitest suite once
npm run test:watch        # watch tests during development
npm run typecheck         # type-check src/ and test/ without emitting
npm run build             # emit declarations, source maps, and dist/cli.js
```

The project requires Node.js `>=20.19`. Use the committed `package-lock.json` with npm.

## Coding Style & Naming Conventions

Use strict TypeScript with native ESM imports, including `.js` extensions in local imports. Follow the existing two-space indentation and compact, explicit functions. Use `camelCase` for variables/functions, `PascalCase` for types/classes, and descriptive `*.test.ts` filenames. Reuse existing dependencies and error types; there is no separate formatter or linter script, so keep changes consistent with neighboring code and run `npm run typecheck`.

## Testing Guidelines

Write focused Vitest tests beside the affected behavior, using `describe`/`it`. CLI and filesystem tests must use the temporary `SPM_HOME`/`HOME` helpers so they never touch a developer’s real configuration. Cover idempotence, invalid input, and filesystem safety when changing reconciliation or discovery logic.

## Commit & Pull Request Guidelines

Use short imperative Conventional Commit-style subjects such as `feat:`, `fix:`, `docs:`, or `chore:`. Keep commits focused. Pull requests should explain the behavior change, identify affected commands or manifests, list validation commands and results, and update documentation/tests when user-visible behavior changes. For CLI changes, include representative command output when it clarifies the review.
